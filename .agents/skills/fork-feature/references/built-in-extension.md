# Adding a fork built-in extension

Model: `extensions/debug-auto-launch` (one `src/extension.ts`, Node only, no proposals, `devDependencies` only `@types/node`). For proposed API usage, compare `extensions/tunnel-forwarding` (`enabledApiProposals` + proposal `.d.ts` in `tsconfig.json`). Name fork extensions `extensions/vsade-<feature>/`, package `name` `vsade-<feature>`. Keep `"publisher": "vscode"` like every other built-in (all but `extensions/copilot` in `extensions/*/package.json`): `src/vs/workbench/api/common/extHostTelemetry.ts` special-cases it, and the extension id becomes `vscode.vsade-<feature>`. Command/setting/context-key ids still use the `vsade.` prefix.

## Files to create (all fork-owned)

```
extensions/vsade-<feature>/
	package.json        2-space indent (hygiene exempts package.json; .editorconfig says spaces)
	package.nls.json    tab indent; every %key% used in package.json
	tsconfig.json       tab indent
	esbuild.mts         Microsoft copyright header, tabs
	.vscodeignore       copy from the model
	src/extension.ts    Microsoft copyright header, tabs
	media/icon.png      optional (the model has one)
```

`package.json` (copy the model, change names):

```json
{
  "name": "vsade-<feature>",
  "displayName": "%displayName%",
  "description": "%description%",
  "version": "10.0.0",
  "publisher": "vscode",
  "license": "MIT",
  "engines": { "vscode": "^1.82.0" },
  "capabilities": { "virtualWorkspaces": true, "untrustedWorkspaces": { "supported": true } },
  "extensionKind": ["ui"],
  "enabledApiProposals": [],
  "activationEvents": ["onStartupFinished"],
  "main": "./out/extension",
  "contributes": {
    "commands": [{ "command": "vsade.<feature>.<action>", "title": "%command.<action>%", "category": "%category%" }]
  },
  "scripts": {
    "compile": "gulp compile-extension:vsade-<feature>",
    "watch": "gulp watch-extension:vsade-<feature>"
  },
  "devDependencies": { "@types/node": "24.x" }
}
```

- `main` points at `./out/...`: in dev the gulp task compiles `src/` to `out/` with tsgo; the packaged build bundles with `esbuild.mts` into `dist/` and `fromLocal` in `build/lib/extensions.ts` rewrites `main` from `/out/` to `/dist/` and strips `scripts`/`dependencies`/`devDependencies`.
- `extensionKind: ["ui"]` keeps it in the local extension host for remote windows and out of the remote server build (`isUIExtension` filter in `build/gulpfile.reh.ts`). Omit it for workspace extensions.
- Production `dependencies` require `esbuild.mts` bundling; without it `fromLocalNormal` throws ("has production dependencies ... but is packaged without bundling").
- Web: only if needed, add `"browser"`, `esbuild.browser.mts` and `tsconfig.browser.json` (see `extensions/references-view`); `isWebExtension` in `build/lib/extensions.ts` decides web packaging.

`tsconfig.json` (from the model):

```json
{
	"extends": "../tsconfig.base.json",
	"compilerOptions": { "rootDir": "./src", "outDir": "./out", "types": ["node"] },
	"include": ["src/**/*", "../../src/vscode-dts/vscode.d.ts"]
}
```

`esbuild.mts`: identical to `extensions/debug-auto-launch/esbuild.mts` (calls `run` from `extensions/esbuild-extension-common.mts`, `platform: 'node'`, entry `src/extension.ts`, outdir `dist`).

`.vscodeignore`: `src/**`, `tsconfig*.json`, `**/*.tsbuildinfo`, `out/**`, `esbuild*.mts`, `package-lock.json` (as in the model). Packaging lists files through `vsce.listFiles`, which honors it.

## Upstream registrations (each is an upstream-owned file: marker or ledger, and listed in the PR body)

| File | Edit | Why | Marker |
|---|---|---|---|
| `build/gulpfile.extensions.ts` | add `'extensions/vsade-<feature>/tsconfig.json',` to the `compilations` array | creates `compile-extension:`/`watch-extension:`/`transpile-extension:vsade-<feature>`; `transpile-extensions` (used by `pnpm run build-fast` via `build/next/build-fast.ts`), `compile-extensions` and `watch-extensions` iterate this list. Without it `out/` is never built in dev | `// FORK:` line above |
| `pnpm-workspace.yaml` | add `  - extensions/vsade-<feature>` under `packages` | makes it a pnpm workspace member so `@types/node` (and any deps) install | `# FORK:` line above |
| `build/npm/dirs.ts` | add `'extensions/vsade-<feature>',` to `workspaceMembers` | the build's own copy of the member list (`getLockfileFolder` in `build/lib/pnpmLock.ts`, `build/lib/dependencies.ts`, CI cache keys); keep it identical to `pnpm-workspace.yaml` | `// FORK:` line above |
| `pnpm-lock.yaml` | regenerated by `pnpm install` (adds an `importers` entry like `extensions/tunnel-forwarding:`) | lockfile | ledger line in `scripts/vsade/fork-patches.txt` (generated; on merge conflict take upstream's and rerun `pnpm install`) |

Place each entry next to a stable neighbour rather than at the end of the list, with the marker line directly above it. Nothing else needs registering:
- Packaging is automatic: `doPackageLocalExtensionsStream` in `build/lib/extensions.ts` globs `extensions/*/package.json` (minus `excludedExtensions` and `product.json` `builtInExtensions`), and `build/gulpfile.reh.ts` globs the same for the server.
- NLS: `package.nls.json` is picked up by the scanner (`scanBuiltinExtensions`/`translatePackageJSON` in `build/lib/extensions.ts`) and by `build/lib/i18n.ts`.
- `extensions/package.json` holds only shared deps (`typescript`, `esbuild`, ...); do not edit it.
- `eslint.config.js` mentions some extensions only in rule `ignores` lists; a new extension needs nothing there if it lints clean.

Unverified shortcut: an extension with no `devDependencies` (tsconfig `"types": []`, no Node APIs) might skip the `pnpm-workspace.yaml`/`dirs.ts`/lockfile edits. Every TS extension in `compilations` today is a workspace member, so prove it compiles before relying on it.

## Proposed API

- Declare each proposal in `package.json` `enabledApiProposals` and add `../../src/vscode-dts/vscode.proposed.<name>.d.ts` to the tsconfig `include` (as `extensions/tunnel-forwarding/tsconfig.json` does).
- Built-in extensions keep their declared proposals unconditionally: in `src/vs/workbench/services/extensions/common/extensionsProposedApi.ts` the declaration is only nulled for `!extension.isBuiltin`. So no `product.json` change is needed. Do not add a built-in to `product.json` `extensionEnabledApiProposals`: if listed there, the product list *replaces* the package.json list.
- Running out of sources (`!isBuilt`) every extension gets proposals; `extensionEnabledApiProposals` matters only for non-built-in (VSIX/gallery) extensions in a packaged build.
- Unknown proposal names are dropped with a log error ("that proposal DOES NOT EXIST"); upstream finalizes or deletes proposals, so recheck after merges.
- A brand-new fork proposal means a new `src/vscode-dts/vscode.proposed.<name>.d.ts` (fork-owned), regenerating `src/vs/platform/extensions/common/extensionsApiProposals.ts` with `pnpm run gulp compile-api-proposal-names` (generated, ledger line in `scripts/vsade/fork-patches.txt`), and an implementation in `src/vs/workbench/api/common/extHost.api.impl.ts` plus a main-thread side: that is rung (e) work with several upstream hunks; prefer rung (d) instead.

## Build, run, debug from sources

- Install after adding the workspace member: `pnpm install` (root).
- Compile once: `pnpm run gulp compile-extension:vsade-<feature>`; watch: `pnpm run gulp watch-extension:vsade-<feature>`; or everything via `pnpm run build-fast` / the `Watch` task (`pnpm run watch-extensions` covers all `compilations`).
- Run: `./scripts/code.sh` (sets `VSCODE_DEV=1`). In dev the built-in extensions folder is `extensions/` itself (`builtinExtensionsPath` in `src/vs/platform/environment/common/environmentService.ts`), so the extension loads from `extensions/vsade-<feature>/out/`.
- Debug: the dev extension host listens on port 5870 by default (`parseExtensionHostDebugPort` in `src/vs/platform/environment/common/environmentService.ts`); use the `Attach to Extension Host` config in `.vscode/launch.json` (its `outFiles` already include `extensions/*/out/**/*.js`). Alternatively copy the `Launch Built-in Extension` config with `--extensionDevelopmentPath=${workspaceRoot}/extensions/vsade-<feature>`. The `launch` skill automates launching plus debugger attach.
- Packaged check (slow, only when shipping): `pnpm run gulp vscode-darwin-arm64` writes `../VSCode-darwin-arm64/` next to the repo (`buildRoot` in `build/gulpfile.vscode.ts`); the extension must appear under `.../Contents/Resources/app/extensions/vsade-<feature>/` with `dist/`.
- Validation commands: `validate-change` skill.
